# 共有仕事APIと運用境界

2026-09-13。共有仕事、人とPCのプロジェクト参加、担当交代、操作承認、会話・成果、環境配置をHubで永続管理します。Runnerが通常エージェントを実行し、Desktopが一般利用者の仕事画面を提供します。旧MCP jobs / 端末履歴とは別の保存契約であり、既存の仕事を自動移行しません。

## 保存と認証

Hubの保存先に`shared-work.sqlite3`を追加し、forward migrationで共有仕事、identity、操作承認、会話・成果の参照を保存します。大きな内容は隣接する`shared-work.assets/`へ保存します。catalog、CA、端末ネットワークのJSONは維持します。バックアップ・復元は後述の停止したHubの保守CLIを使います。

管理者はloopbackのWeb画面で初回登録します。人のセッションは`web_admin`と`shared_work`を分離します。共有用セッションは、実TLS接続で確認した端末IDにも結び付きます。端末証明書だけで利用者を推定しません。管理者も明示的なプロジェクト所属なしで仕事の本文を閲覧できません。

Web管理画面の変更には、現在の管理者cookie、CSRF、Origin、画面が取得したセッション識別子を要求します。別タブで本人が変わった旧画面の操作は拒否します。loopback以外の平文HTTPではパスワードの送信・管理操作を許可しません。一般利用者はDesktopから共有APIへ認証し、Hub管理画面を使用しません。

プロジェクトの役割は `reader` / `contributor` / `manager` です。通常の管理画面ではプロジェクトごとに参加者と役割を指定します。既存のグループによる有効な役割は移行時に維持し、そのプロジェクトを新画面で保存すると、表示された有効参加者を個別の参加者へ置き換えます。他のプロジェクトは変更しません。所属の無効化は新しい閲覧、仕事受付、承認、実行資格へ反映します。人の資格世代と仕事の実行権限世代を分け、パスワードや所属の変更後に古い判断を再利用しません。

## 相互TLS内のAPI

端末ネットワークを開始すると`/v1/shared/`以下を提供します。端末証明書がない要求やブラウザーOrigin付き要求は拒否します。人が使うAPIは、`POST login`で得たtokenを`Authorization: Bearer ...`として送ります。セッションを別の端末証明書へ持ち替えることはできません。

| GET `projects` | 本人が所属し、このPCから操作することを許可されたプロジェクト |
| GET `environments?project_id=...` | 閲覧可能な公開環境と共通枠の占有数 |
| POST `jobs` | 共有根仕事の永続受付 |
| GET `jobs?project_id=...&before=...&limit=50` | プロジェクト内の仕事。最大100件 |

V12以降に画面で保存したプロジェクトでは、本人の役割と操作用PCの指定の両方を要求します。一覧・通知・占有の人名もその交差範囲に絞り、所属外の占有は件数だけを示します。個別の仕事・成果・会話の取得、投入・取消・承認・担当交代・追加指示では、保存ownerを取得した後に現在のPC指定を再検証します。実行専用PCは本人の操作用権限を得ず、自端末の割当・停止報告を端末資格で扱います。旧プロジェクトは登録済みPCからの操作という従来の範囲を維持し、明示保存時に選択PCへ切り替わります。

厳密なpayloadと上限は`src/shared_work/`の公開型とtestsを正とします。Desktop内蔵の実行設定と運用はmoyAI側の `docs/runner-shared.md`、一般利用者の操作は `docs/shared-work-desktop.md` を参照してください。旧端末やMCPクライアントは、自動でこの配送契約に対応しません。

`claim`に `{"environment_ids":["analysis"]}` を指定すると、初回割当と未開始試行の再送をその集合に絞ります。指定は空でない128件以内、重複不可です。省略時は従来の全環境を対象とします。割当の `allowed_child_environments` は現在の担当者がそのプロジェクトで使用できる環境です。Desktopの初回実行許可から作成した標準環境では、この範囲への子の仕事の委任も初回確認に含みます。手動設定の環境では、Runner管理側の明示allowlistとさらに交差させます。

`GET runner/assignments?environment_ids=analysis,solver` は、現在の実証明書の端末が所有する指定環境の試行・停止要求だけを返します。最大128件、重複・不正IDは拒否します。削除済み・別端末の環境は対象外とし、古い設定が混在しても正常な環境の停止配送を妨げません。`environment_ids=` は空集合、query省略は旧互換の全件返却です。省略したpollを全環境の通信確認には使いません。

仕事の要約・詳細・環境は `runner_contact: {last_contact_ms, state}` を返します。`state` は `unconfirmed`（未確認）、`recent`（最後の確認から15秒未満）、`stale`（15秒以上応答未確認）で、Hubが判定します。DesktopがHubから状態を取得した時刻や、端末の通常presenceとは別の観測です。明示した環境集合での成功したclaim/assignmentsは、その環境と返した試行の接触を記録します。個別の試行照会・報告・副作用資格確認・入力/会話/成果のデータ要求は、成功した正確な試行だけを更新し、環境全体の受付確認にはしません。

この表示は共有APIの通信確認であり、モデル・子プロセスの進捗や正常動作の証明ではありません。未確認・応答待ちでも仕事の状態、結果、共通枠を変更しません。占有0でも通信未確認の環境を受付可能とは断定しません。観測はHubの共有owner内で環境1024件・試行4096件に制限し、古い観測から退役します。終了済み試行は新しい接触として記録せず、Hub再起動・復元では観測を空に戻します。そのため古い保存時刻が新しい応答として表示されることはなく、再接触までは `unconfirmed` / `last_contact_ms: null` です。

`status` は `next_before` と `next_environment_before` を独立して返します。同じ資源IDの占有はプロジェクトをまたいで数えます。所属するプロジェクトの占有仕事だけを最大5件表示し、同じ権限内の残件数は `additional_visible_occupants`、所属外の占有数は `other_occupants` として返します。所属外の仕事のID・件名・利用者名は返しません。管理者権限だけでこの表示範囲は広がりません。

`inbox` の通知と未読件数も現在の所属で絞ります。通知の元は仕事・承認・担当交代の保存記録であり、別の仕事状態を持ちません。既読だけを本人単位で保存します。閲覧者へ操作権限は付与せず、承認の実行可否は現在の担当者またはManagerの資格で再計算します。

## 受付・開始・停止の境界

`status.execution_devices` は、このプロジェクトに割り当てた実行PCを環境作成前から返します（最大128件）。各PCの `device_id`、`device_label`、`environment_id`、`preparation_state`、`error` を含み、準備状態は既存の初回設定・配置情報から求めます。環境と仕事要約にも `device_label` を返し、PC名は取得時点の端末登録を参照します。プロジェクト名・環境名へPC名を複製保存しません。この投影も本人の所属と操作PCの認可を通し、別プロジェクトのPCを追加開示しません。

同じ利用者の同じ`request_id`と同じ内容は既存仕事を返します。内容が異なれば409で拒否します。子孫の予算は根仕事の受付時に有限に確保し、外部受付枠を子・孫に要求しません。上限到達は429として明示し、無制限に待機させません。

`SubmitJob` と追加指示には任意の `start_before_ms`（UTC epoch milliseconds）を指定できます。Hubが受け付ける時点より後が必要で、省略した新しい根仕事は受付から24時間です。確定した期限を仕事に保存し、同じ要求の再送では延長しません。子は親の期限を引き継ぎ、子の終了後に親を再開する試行にも同じ期限を適用します。追加指示は別の根仕事なので新しい期限を持ちます。V9以前の仕事はV10で作成日時から24時間、子孫は根の期限以下へ移行します。

割当と`Started`の確定時に期限を照合します。期限切れの待機仕事と、開始許可のないことが確定している準備試行は `failed` とし、`result.error=start_deadline_exceeded` と人が読める `message` / `wait_reason` を返します。状態が不明な準備試行は停止確認まで利用枠を保持します。すでに`Started`が確定した実行は、期限だけでは中止せず結果を受け付けます。通常のAPI利用と画面の状態照会でも一回128件以内で期限切れを清算するため、端末が戻らなくても順次理由を確認できます。期限経過は不明な実行の再配分許可になりません。

根仕事の受付時に利用可能な環境IDの上限集合を保存します。以後の設定変更や担当交代で集合を広げず、現在の担当者の資格と交差して使用します。依頼者、現在の担当者、受付枠の計上先は別の事実として保持し、子への委任や担当交代で元の受付枠を付け替えません。

`claim`は準備用の試行と共通資源枠を確保します。初期版は一つのRunnerの未完了試行を最大128件とし、照会・停止要求から欠落する割当を作りません。共有Runnerは起動意図を独立したSQLite journalへ保存し、`Started`がHubで受理されたことと現在の試行状態を確認してから副作用を開始します。応答不明は同じ試行・報告IDで照合し、別IDの再起動で回避しません。

共有APIは保存処理の待機後にも端末の実証明書と現在の資格を確認し、実行許可を確定する操作では端末の利用可否も再確認します。その確認からDBの確定までは端末管理の同じlockを保持するため、待機中に利用停止・資格失効が確定した要求を、古い判定で実行開始や承認配送へ進めません。

`YieldToChild`はcheckpoint保存・子作成・親の待ち先を一つのtransactionで確定します。Runnerがプロセスと必要な資源の安全な返却を確認していなければ拒否します。子の結果保存は親を一度だけ再開可能にし、次の試行へcheckpointと子の結果を返します。

新しいversion 2 checkpointでは、同じ試行・世代の会話アーカイブを先にHubへ保存し、その中のcheckpointと報告内容が一致していなければ子待ちを受理しません。Runnerはアーカイブの正確な会話・turn・履歴digestを検証して再開します。旧version 1 checkpointは同じRunnerの保存履歴を必要とする互換経路です。

取消受付だけでプロセスの停止や資源解放を確定しません。発行済み試行は停止確認待ちに残ります。切断・再起動・期限経過だけで別試行へ再配分しません。rootが取消済みなら、後着の結果は照合に使い、親を再開しません。

Runnerが副作用の有無を確定できなければ `Uncertain` を記録します。仕事と資源を保持し、同じ試行の開始や子生成を拒否します。停止を確認した `Finished` が資源解放を所有します。失効した端末にも、自端末の既存試行に対する停止照合・不確定報告だけは実証明書の確認後に許可します。新規割当・開始・委任・承認受取は許可しません。

## 人の操作承認

`ApprovalRequested` は、Runnerの正確な操作ID・操作内容・期限をHubへ保存します。実行中かつ未取消・不確定でない試行に限定し、同時に未消費の有効な要求は一件、試行当たり累計1000件、期限は最大15分です。判断はプロジェクトの現在の担当者（Contributor以上）またはManagerに限ります。管理者であることだけでは承認できません。

同じ承認への同じ人・同じ回答は照合できます。別の回答で上書きしません。Runnerの受取時にも試行ID・世代・所有端末・取消・期限・判断者と担当者の現在の権限を再確認します。`consumed` は回答が配送された記録であり、副作用の完了を意味しません。回答の応答喪失時は同じ内容を再配送できますが、期限・取消・権限失効後に過去の許可は返しません。

各副作用の直前にも `authorize` で仕事の権限世代と現在の資格を確認します。人の判断を要した操作は正確な承認IDも渡します。途中で失効した許可を、新しい操作へ流用できません。緊急停止は新しい実行許可を必要としません。

担当交代で待機中の承認が失効した場合、Hubは同じ実行端末・試行・世代が現在も実行資格を持つことを確認し、専用の再確認応答を返します。Runnerは中断中の操作を維持したまま承認IDだけを更新し、同じ内容を再提示します。旧IDの回答は使用できず、再提示だけで操作を実行したり資源を返却したりしません。一般の競合エラー、通信断、期限切れ、取消、資格失効を再確認の許可として扱いません。

## 担当交代と追加指示

担当者またはManagerが根仕事のrevisionと新担当者を指定します。新担当者にはContributor以上が必要です。未開始の割当はそのまま開始させず、実行中の試行がある場合は交代を保留します。実行中の試行は旧担当者の資格で処理を続け、子待ち・終了によって全試行が安全地点へ到達したときに未終端仕事の担当と権限世代を更新します。要求時点の旧承認は失効しますが、保留中の実行に必要な新しい承認要求は受け付けます。取消が先に確定した根仕事では担当交代を成立させません。

準備中でも `Uncertain` が記録された試行は担当交代で解放せず、`stop_requested` として同じ枠を保持します。実行端末の正確な停止報告または管理者の停止照合が完了してから交代を適用します。その間に親の開始期限を過ぎた場合、親は再開せず期限超過で終端化し、保留中の交代も成立させません。

追加指示は終端状態を巻き戻しません。保存済み会話がある終端仕事から、新しいrequest_idで別の根仕事を作り、元の仕事を `continued_from` として参照します。入力参照と元の会話を引き継ぎ、元の権限上限と現在の本人資格の範囲で新しい実行を受け付けます。

## 会話・入力・成果

入力と成果は、SHA-256をファイル名とするHub専用領域へ固定保存し、DBへ長さ・公開名・所有する仕事とプロジェクト・内容ハッシュを記録します。通常ファイルは8 MiB、会話アーカイブは64 MiB、保持する内容の論理合計は2 GiBが上限です。同じアップロードIDと内容は既受理データを返し、異なる内容は拒否します。停止後に新たな実行資格を付与することなく、既受理アップロードの応答喪失を照合できます。

ファイルを同じ保存ディレクトリで書き込み・同期してからDBの参照を確定します。既存ハッシュのファイルは長さと実内容を確認し、上書きしません。読取もディレクトリとファイルのhandleで確認し、reparse先への差替えや内容不一致は拒否します。保存中に失敗した未参照ファイルは、既存の保存ownerが一回128件以内で回収します。V8以前のDB内BLOBはV9移行で全内容の永続保存を確認してから空にし、失敗時は旧内容とschema markerを維持します。

今回の運用・実証対象はWindowsです。Windowsでは親ディレクトリをrenameできない共有モードで保持し、読取中のファイルの書換え・renameも共有モードで拒否します。Unix側は信頼するHub専用ディレクトリを前提とし、リンク拒否と開いたinodeの照合を行いますが、dirfd基準の配置・削除まで同等の競合耐性を実証したものではありません。

Runnerの新しいダウンロードは、試行・現在の担当者・権限上限・取消・停止状態を確認します。仕事へ入力として結び付いていない別ファイルをRunnerが取得することはできません。人の閲覧・ダウンロードにも現在の所属が必要です。

`shared_publish_artifact` は共有実行だけで使用するツールです。shellやsolverが作ったバイナリを環境内の相対パスで指定し、元ファイルを変更せず固定コピーをcanonical ToolResultへ記録します。コピーを会話アーカイブのsidecarとして運び、元ファイルが後から変更されても同じ成果を共有します。任意の端末絶対パスや環境外のファイルは公開対象にできません。

会話に付属する出力コピーは、長文ツール出力も含めて一会話128件・合計32 MiB、各8 MiB以内です。成果ツールは正本の既存参照を数えて保存前に残容量を確認します。Agentは同じLLM応答内の複数ツールも一件ずつDBへ確定してから次へ進むため、複数の公開要求が未保存の容量を重複して使うことはありません。

## 管理と環境配置

ブラウザーの「プロジェクト・利用者」で、最初に「利用者」から利用者を登録します。PCの参加申請を許可したら、「プロジェクトを追加」で名前、参加者の役割、操作に使うPC、仕事を実行するPCを選び、一度保存します。同じPCを両方の用途にも、複数プロジェクトにも選べます。利用者が識別子・テンプレート・共有枠を入力する必要はありません。

実行用PCの初回設定が終わっていなくても、プロジェクトの指定は保存できます。そのPCのDesktopが保存先と操作権限の初回確認を受け、標準の作成設定を公開すると、Hubがプロジェクト専用の作業場所を自動的に依頼します。画面は「このPCの実行設定待ち」「作業フォルダを準備中」「利用可能」「準備できません」を表示します。「利用可能」は作業場所の準備記録であり、PCの現在の通信・実行状況はDesktopのRunner応答と仕事の状態で確認します。失敗は理由を残し、「準備を再試行」で同じ場所の準備を依頼します。

同じPCの自動実行場所は、プロジェクトが異なっても一つのPC資源・容量1を共用します。既存の単一実行場所・共有枠は再利用します。旧設定に複数の実行場所や分離した共有枠があり一意に決められない場合は、勝手に並列枠やフォルダを増やさず、管理者の整理が必要な理由を表示します。PCの選択を外しても履歴と保存された実行場所は保持し、そのプロジェクトの新規利用だけを止めます。他のプロジェクトの選択や占有を削除しません。

保存は一つの管理transactionで参加者・PC用途・準備要求を確定し、現在revisionと同じ要求IDの内容を照合します。別画面の変更と衝突した場合は入力を保持して再確認を求めます。応答喪失時は同じ内容の受付を確認し、別の実行場所を重複作成しません。

旧グループ・実行場所・資源のデータと互換APIも同じ保存ownerで維持します。既存仕事や権限上限が参照する環境のRunner・資源は付け替えできません。別の実行先には新しい環境IDを作成します。参照される人・環境等の削除も拒否し、停止・無効化を利用できます。

通常のプロジェクト保存では標準の作成設定を自動で選び、Hubが世代付きの配置要求を保存します。既存の手動配置APIでは、明示したテンプレートへの要求も扱います。ローカルのbase root、実パス、固定access modeはRunner側の許可設定が所有します。Hubの入力から任意パスを指定しません。成功ACKまでその環境へ仕事を割り当てず、失敗後の再要求も現在の配置世代を照合します。

登録した物理資源を使うローカル入口は `local-admissions` で実本人の共有セッションを確認し、通常のHub枠と同じtransactionで資源を確保します。満杯なら即時拒否し、別の待ち行列へ逃がしません。この試行は通常の共有claimから除外し、既存ローカル実行と二重起動しません。端末全体を共通資源にする既定の参加設定と、明示的に分離したworkspace設定はmoyAI側のRunner設定を参照してください。

## 保守と検証範囲

管理画面で停止確認を行う場合、対象の正確な試行ID・世代と理由を指定します。管理者が実プロセス停止を確認したことを明示し、保存上は失敗または取消へ終端化します。切断だけから成功や安全な再実行を推定しません。

保持期限の削除は自動で行いません。管理画面のプレビュー後、設定revision付きの削除要求で同じ条件を再評価します。未終端仕事の入力・続行が必要とする内容は保護し、削除してもメタデータと受付照合記録を保持します。削除済み内容を新しい入力へ再利用することはできません。物理ファイルは削除状態のDB確定後、同じハッシュへの保持中の参照がなくなった場合だけ回収します。別の仕事・プロジェクトが同じ内容を参照していればファイルを保持します。

停止中のHubで `--backup-dir PATH` を実行すると、保存ファイルのチェックサム付きバックアップを作成します。バックアップ先と復元先は、親フォルダだけを用意し、指定するフォルダ自体はまだ存在しない場所を使います。バックアップにはCAや利用者情報も含むため、Hub管理者が管理する保存先を指定します。

```powershell
moyai-hub --data-dir C:\moyAI\Hub --backup-dir C:\moyAI\Backups\Hub-20260913
moyai-hub --restore-from C:\moyAI\Backups\Hub-20260913 --data-dir C:\moyAI\Hub-restored --acknowledge-runners-stopped
```

復元には関連Runnerと管理プロセスの停止確認が必要です。復元後は人のセッション・旧承認を失効し、端末・環境を停止します。保存時に待機中だった仕事も、その後実行された可能性があるため根仕事全体を取消対象にします。発行済み試行がない根は取消を確定し、未完了試行がある根は不確定な停止確認待ちとして資源を保持します。保留中の担当交代も取消へ閉じ、終端済み仕事の結果を巻き戻しません。環境を再び有効にしても古いキューを実行せず、再実行には新しい明示的な依頼が必要です。途中で失敗した復元先には起動禁止markerが残るため、それを削除せず、原因を解消して別の新規保存先へ復元します。

このAPI仕様は物理複数Windowsでの運用受入や長時間負荷試験の完了を意味しません。製品ごとの実施済み試験と実環境の証跡はtask-localの検証結果を参照してください。
